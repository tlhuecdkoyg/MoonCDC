# REAL 精度验收问题修复说明

对应版本：MoonCDC **0.2.0**（2026-11-06）。

## 问题与根因

0.1.0 捕获触发器使用 SQLite `printf('%!.26g', value)` 将 REAL 转为十进制文本。实测 Windows/MSVC 下内置 SQLite 3.49.1 对 `1e300` 输出 `9.99999999999999956e+299`，该文本解码后的 binary64 值与原值相差 1 ULP：

| 环节 | IEEE 754 binary64 位模式（十六进制） |
| --- | --- |
| 源库直接读取的 `1e300` | `7e37e43c8800759c` |
| 旧触发器输出文本解码后 | `7e37e43c8800759b` |

因此增量插入可能改变数值；若目标由正确快照初始化，后续更新即使只改变其他列，也可能因日志中的 REAL before-image 已失真而发生冲突。0.1.0 关于该路径无损的说明不成立。

## 修复方式

- REAL 改为三元编码 `['real', '有符号整数有效位', '二进制指数']`，语义为整数有效位乘以 2 的整数次幂。
- 持久化触发器用纯 SQLite SQL 完成 11 级精确二次幂缩放；二次幂由 `2.0` 逐级平方生成，最终有效位转为整数文本。外部连接不需要注册扩展函数。
- MoonBit 编码从 binary64 位模式提取有效位和指数，解码通过整数运算构造位模式；不经过实数十进制格式化，也不以近似浮点乘法重建结果。
- 对不可精确表示、溢出和非有限值的输入拒绝解码；保留严格 before-image 冲突检查，不以容差或跳过事件掩盖分歧。

## 回归验证

运行 `python scripts/verify.py`，新增测试包括：

1. `1e300` / `-1e300` 的直接、JSON 与 JSONL 快照初始化，随后仅更新其他列、更新 REAL、重复应用与删除。
2. 独立 Python `sqlite3` 写入及 `struct.pack('>d')` 逐位比较，覆盖 **5,134 个有限 REAL 样本**：全部有限指数的正负扫描、随机模式、最大有限数和次正规数；连续三轮更新后再删除并审计。
3. MoonBit 核心编解码的随机位模式与边界测试，包含负零；原生、JavaScript、wasm-gc 均执行适用测试。
4. 人为将目标 REAL 改动 1 ULP，确认真实冲突仍导致整批回滚，目标游标与源端确认不前进。

2026-11-07 补充自查发现：BLOB/无类型列可以实际保留负零，而纯 SQL 捕获不能可靠识别其符号。0.3.0 明确将数据库快照和捕获中的 REAL 零统一规范化为正零；非零有限 REAL 保留位模式，独立 wire 编解码仍保留负零。详见[本轮自查报告](REVIEW-20261107.md)。

## 旧版本数据处理

0.2.0 仍可读取旧二元十进制 REAL 编码，但旧日志中已经丢失的原始位模式不能从文本推断恢复。旧触发器也不会被新验证逻辑接受。已有 0.1.0 捕获与目标应按照 [迁移步骤](OPERATIONS.md) 从权威源表建立新捕获、新快照和新目标，审计通过后切换，保留旧库备查。
